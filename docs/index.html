Introduction to Xenium data

Before we start to work with the Spatial Transcriptomics data from this study, we will provide an introduction previewing some of the specifics of Xenium data: how it’s generated, what is produced or generally what you can expect working with it, and any special considerations to keep in mind when working with Xenium data. Some of these topics will be discussed in more detail throughout the case study.

Data generation

Xenium is an image-based spatial transcriptomics platform.

Cell segmentation for v1 utilizes DAPI for nucleus and an isotropic nuclear expansion algorithm to approximate the cell boundaries. An alternative approach (not used in the process of this paper)

Data products

Summary

In Summary, Xenium data utilizes a gene panel of probes to assay the spatially-resolved expression of specific genes at a cellular or subcellular resolution within tissue samples. Samples used to generate Xenium data are either fresh frozen (FF) or formalin-fixed paraffin-embedded (FFPE) tissue samples. After sample preparation, imaging cycles are performed using a Xenium Analyzer. Cellular segmentation is performed to approximate boundaries between cells.

What are the data?

Xenium spatial transcriptomics data represents mRNA counts for panel target transcripts mapped to spatial locations in the tissue. As such there are 3 main data types or files that we will be working with.

  1. Tissue/sample Metadata
  2. Spatial Coordinates
  3. mRNA Counts

Metadata

For the data in Kwon et al. (2026), postmortem tissue samples from 24 donors were used to generate Xenium data:

  • 12 Neurotypical donors [NTC]
    • 5 males
    • 7 females
  • 12 donors diagnosed with Schizophrenia [SCZ]
    • 6 males
    • 6 females

Spatial Coordinates

We have {Sample}-cell_boundaries.csv.gz files for the spatial coordinates rather than classical files with spatial coordinates (….add explanation of what these classical files/other options are). Specifically these files have many rows per cell describing each vertex that is part of a cell polygon. We can find the centroid of each cell by considering all of these polygon coordinates together.

For each row:

  • cell_id
  • vertex_x
  • vertex_y

Note that the Cell IDs in these files correspond to the $barcodes discussed in the RNA counts data

RNA counts

The data for the RNA counts is stored in .h5 files. Rather than storing large matrices, the data is more efficiently stored in named/nested lists that can be used to reconstruct the matrix. Of important note, only non-zero counts are stored as well as the indices where those counts are in the matrix (e.g., for which genes and spot IDs they correspond with). Information here: https://www.10xgenomics.com/support/software/space-ranger/latest/advanced/hdf5-feature-barcode-matrix-format

Can use rhdf5::h5dump(file_name, load = FALSE) to get a look at the names or headers of the data.

  • $matrix is the top name
    • $barcodes – cell IDs
    • $data – the non-zero counts
    • $features – has subparts relating to the rows/genes
      • $_all_tag_keys – “genome” for our data
      • $feature_type – specifies Gene Expression vs negative control probe, negative control codeword, unassigned codeword
      • $genome – unknown for our data
      • $id – gene ID or control/probe ID for elements of $data
      • $name – gene name or control/probe name for elements of $data
    • $indices – zero based row index for non-zero values found in $data (i equivalent for Matrix::sparseMatrix)
    • $indptr – zero based index for $data and $indices where columns start (p equivalent of Matrix::sparseMatrix)
    • $shape – dimensions of the data (number of genes or features X number of cells).
      • Note that the number of cells >>>>> number of genes (Xenium panel with limited number of genes)
      • Note that the product of the dimensions will be greater than the length of $data since this is representing non-zero counts only and therefore is a sparse representation

What spatialGE is looking for

spatialGE will accept file directories, but it will also accept lists of dataframes for each sample. Because we have to wrangle our generic format input data, we’ll be providing named lists of dataframes for both the spatial coordinates (spotcoords) and the feature counts (rnacounts).

For spatial coordinates, the dataframes should have

  • 3 columns
    • Spot or Cell IDs
    • X value (center)
    • Y value (center)
  • One row per each unique spot or cell ID

For the feature counts, the dataframes should have

  • n features/rows
  • (m+1) spots or cells/columns
    • The plus 1 is because the first column will list the feature/gene names

For samples metadata (if passing a dataframe with additional metadata beyond sample names), the sample names used in the named lists for spotcoords and rnacounts should be the first column of the samples dataframe.

decompress_read_parquet <- function(samples_metadata, sample){
  #Build file paths
  gz_file <- here(paste0("data/raw/",
                         sample,
                         "/",
                         sample,
                         "_",
                         samples_metadata[which(samples_metadata$sampleID == sample), "brainNumID"],
                         "-cells.parquet.gz"))
  
  decompressed_file <- str_replace(gz_file, ".gz", "")

  #Decompress
  R.utils::gunzip(gz_file, destname = decompressed_file, remove = FALSE, skip = TRUE)

  #Read in
  df <- arrow::read_parquet(decompressed_file)

  #Remove the decompressed file because we no longer need it
  file.remove(decompressed_file)
  
  #Select columns of interest
  centroids <- df %>%
    select(cell_id, x_centroid, y_centroid)

  #reclaim some R resources
  rm(df, gz_file, decompressed_file)
  gc()

  #Return
  return(centroids)

}

read_rna <- function(samples_metadata, sample){

  h5file <- here(paste0("data/raw/",
                         sample,
                         "/",
                         sample,
                         "_",
                         samples_metadata[which(samples_metadata$sampleID == sample), "brainNumID"],
                        "-cell_feature_matrix.h5"))
                              

  rna_h5data <- rhdf5::h5read(h5file, name = "matrix")

  rna_mat <- Matrix::sparseMatrix(i = rna_h5data$indices,
                       p = rna_h5data$indptr,
                       x = as.integer(rna_h5data$data),
                       dims = rna_h5data$shape,
                       index1 = FALSE) %>%
      as.matrix() %>%
      as.data.frame() %>%
      `rownames<-`(rna_h5data$features$name) %>%
      `colnames<-`(rna_h5data$barcodes) %>%
      rownames_to_column("genes")

  rm(rna_h5data, h5file)
  gc()

  return(rna_mat)
}

The STlist object

We can look at the type of an object using the typeof() function.

typeof(scz_spatial)
[1] "S4"

The STlist object is an S4 class in R. This means that the object has “slots”. Slots are accessed using an @, rather than a $.

Typically you would see the names in a list using the names() function. Instead, for an S4 class object you use the function slotNames().

slotNames(scz_spatial)
[1] "counts"       "spatial_meta" "gene_meta"    "sample_meta"  "tr_counts"   
[6] "gene_krige"   "misc"

With an S4 class, you have to pre-specify slots prior to the object’s creation. You can’t add slots as you go through an analysis. Therefore, some of these slots currently have data and others will have data added once some spatialGE functions are used.

If we tried to assign a new slot, we would see an error.

Filtering

Using Control Probes and Codewords

First we create a function that we can use with lapply that takes the filtering thresholds that we found previously as well as the counts matrix as inputs. Notice that the thresholds are named arguments meaning they have default values set to the exact variables we were working with earlier. We find the combined expression within each cell of each of the three associated controls using column sums and identify the cell IDs where the combined expression of any one of these types of controls is greater than or equal to the 99th percentile threshold. Finally, we take a union of the identified cell IDs.

By calling this function with lapply, we’ll have named list (to_remove_all) where the sample name stores a vector of cell IDs that should be removed for that sample.

We use a for loop to then loop through the sample names and actually filter the cell IDs within the count matrix. Recall that the cells correspond to the columns in the count matrix. Our filter is specifically using an exclamation point (!) to specify that if a column name is not the list of cell IDs to be filtered, then keep it.

findOverlap <- function(mat, negcp = negcontrol_probe_cutoff, negcc = negcontrol_cdwd_cutoff, ucc = unassigned_cdwd_cutoff){
    which_negcp <- names(which(mat[startsWith(rownames(mat), "NegControlProbe"), ] %>% Matrix::colSums() >= negcp))
    which_negcc <- names(which(mat[startsWith(rownames(mat), "NegControlCodeword"), ] %>% Matrix::colSums() >= negcc))
    which_ucc <- names(which(mat[startsWith(rownames(mat), "Unassigned"), ] %>% Matrix::colSums() >= ucc))

    to_remove <- union(union(which_negcp, which_negcc), which_ucc)

    return(to_remove)
}

to_remove_all <- lapply(scz_spatial@counts, function(x) findOverlap(x))

for (sample_name in names(to_remove_all)){
    scz_spatial@counts[[sample_name]] <- scz_spatial@counts[[sample_name]][,!colnames(scz_spatial@counts[[sample_name]]) %in% to_remove_all[[sample_name]]]

I tested several color palettes and settled on PuBuGn for several reasons. (Note: this could be a cool side quest to include in the case study)

  1. Easier to distinguish changes in expression (e.g., up vs down regulated). BuRd and Spectral were best for this otherwise.
  2. The lighter color was no longer in the center (as if the log expression values were “centered”) and instead is on the lower level of the spectrum. Spectral was the only other one not centered on white, but it was still centered on a lighter color.
  3. Looking at the result with a color vision deficiency simulator (cvg_grid() from colorblindr) the general conclusions are still possible in my opinion. This wasn’t the case with PrGn, BuRd, or Spectral when I tested them.

combine_counts_annot <- function(matannot, matcount, sample_name, gene_name){
    full_join(
        matannot[[sample_name]][,c("libname", "annot")],

            data.frame() %>% 
            rownames_to_column("libname")
    ) %>% `colnames<-`(c("libname", "annot", sample_name))
}

use_combined_data <- function(mat, gene_name, use = "violin", samples = c("Br1139SCZ", "Br5314CTRL")){
  combined_data <- bind_rows(combine_counts_annot(mat@spatial_meta, mat@tr_counts, samples[1], gene_name),
                             combine_counts_annot(mat@spatial_meta, mat@tr_counts, samples[2], gene_name)) %>%
                      pivot_longer(starts_with("Br"),
                                   values_to = "tr_counts",
                                   names_to = "sample") %>%
                      drop_na()

  if (use == "violin"){
    return(
      combined_data %>%
        ggplot(aes(x = sample, 
               y = tr_counts, 
               fill = sample)) + 
        geom_violin() + 
        facet_wrap(~annot, scales = "free_y") + 
        theme_bw() + 
        scale_fill_viridis_d(end = 0.6) + 
        ggtitle(gene_name) +
        theme(legend.position = "bottom")
    )
  } else if (use == "summary"){
    table_length <- length(unique(combined_data$annot)) * 2
    return(
      combined_data %>%
        group_by(annot, sample) %>% 
        summarize(
              min_exp = min(tr_counts), 
              max_exp = max(tr_counts), 
              avg_exp = mean(tr_counts),
              median_exp = median(tr_counts),
              var_exp = var(tr_counts)
        ) %>% 
    print(n=table_length)
    )
  } else {
    message("No other downstream uses supported besides 'violin' and 'summary'")
  }
}
